ApexStore Documentation

Codebase Audit — August 2026

Scope: apex-store-rs v2.2.7 at commit fc024b7 (branch main). Method: static reading of all 37k lines of Rust under src/, plus a reproducible build in the containerised toolchain added by this audit (Dockerfile.dev, Rust 1.92). Every finding below is anchored to a file:line and, where the claim is behavioural, to a command whose output is quoted.

Critical

C-01 — web::Data<bool> TypeId collision disables authentication entirely

Status: fixed in this pass.

actix-web keys application data by TypeId. Registering two web::Data<bool> values means the second overwrites the first, and every reader of Data<bool> observes the survivor.

start_server registered exactly that pair:

  • src/api/mod.rs:1825 — web::Data::new(config.auth.enabled)
  • src/api/mod.rs:1841 — web::Data::new(config.access_control_enabled)

with the access-control flag registered second (src/api/mod.rs:1872), so it won. Three readers were affected:

  • src/api/auth/middleware.rs:29 (bearer_validator)
  • src/api/auth/middleware.rs:81 (require_permission)
  • src/api/access_control.rs:80 (AccessControlMiddleware::call)

ACCESS_CONTROL_ENABLED defaults to false (src/api/config.rs:73). Therefore, with API_AUTH_ENABLED=true and access control left at its default, bearer_validator returned Ok(req) for every request and require_permission returned Ok(()) at all 59 call sites. Authentication and the entire permission model were inert.

CHANGELOG records this exact behaviour being fixed once before, as issue #178 ("API_AUTH_ENABLED has no effect"). Adding the access-control middleware later silently reintroduced it, because nothing in the type system objected and no test exercises the authenticated path (see M-06).

Both readers also used .unwrap_or(false), so a missing flag meant "allow" — a fail-open default on the security-critical path.

Fix applied: distinct newtypes, api::auth::AuthEnabled and api::access_control::AccessControlEnabled, so the two flags occupy different TypeIds and a future third flag cannot collide either. The auth readers now fail closed when the flag is absent.

C-02 — Encryption at rest silently falls back to an all-zero AES key

Status: partially mitigated (failure is now logged); behavioural fix filed as an issue.

EncryptionConfig::default() is { key: [0u8; 32], enabled: true } (src/storage/encryption.rs:35). An all-zero AES-256 key is publicly known, so data "encrypted" with it is readable by anyone.

StorageConfig::default() sets encryption_enabled: true with encryption_key_path: None (src/infra/config.rs:148), and src/bin/server.rs never reads any encryption variable nor calls .encryption_key_path(...). The conversion at src/core/engine/mod.rs:147 then did:

#![allow(unused)]
fn main() {
.map(|path| EncryptionConfig::from_key_path(Some(path)))
.unwrap_or_else(|| Err(LsmError::InvalidArgument(
    "Encryption enabled but no key path provided".to_string())))
.unwrap_or_default()          // <-- the error is constructed, then discarded
}

The explicit diagnostic was built and thrown away. Out of the box, the server encrypts every SSTable block and WAL frame with an all-zero key and reports success. An unreadable or malformed key file took the same path.

Three further defects compound it:

  1. src/core/engine/compaction.rs:135 and src/core/engine/version_set.rs:68 return EncryptionConfig::default() in the else branch taken when encryption_enabled == false — so disabling encryption turns it on with a zero key for those paths, while EngineOptions::from correctly yields enabled: false. Flush and compaction therefore disagree about whether output is encrypted.
  2. #[serde(default)] on encryption_enabled (src/infra/config.rs:98) yields false, while Default::default() yields true. The same field has two contradictory defaults depending on how the config was constructed.
  3. src/infra/health/scrubber.rs:194 returns valid: false for every LSMSST04 file: "Cannot verify CRC32 of encrypted SSTable without encryption key". With encryption on by default, the integrity scrubber reports 100% of SSTables as invalid, indistinguishable from genuine corruption.

The doc comments actively pointed the wrong way — from_key_path's said None "returns a default (disabled) config", and core/table.rs:87 told callers to "pass EncryptionConfig::default() … when encryption is not needed".

src/api/test_helpers.rs:44 shows the confusion was known: it sets encryption_key_path = Some("/dev/null") to force a bypass.

Fix applied: the swallowed failures now emit tracing::error! on the apexstore::security target naming the all-zero fallback, and the misleading doc comments were corrected. Changing the default itself would make existing zero-key SSTables and WAL frames unreadable, so it needs a migration path and is filed separately.

C-03 — DIR_PATH in docker-compose.yml is never read; container data is not persisted

Status: fixed in this pass.

src/bin/server.rs:29 reads DATA_DIR, defaulting to ./.lsm_data. No binary reads DIR_PATH. But docker-compose.yml set DIR_PATH=/data and mounted the apexstore-data volume at /data.

Consequently the server wrote to /app/.lsm_data — inside the container's writable layer, not the volume. Every write was lost when the container was recreated, while the deployment appeared to have a persistent volume.

INDEX_INTERVAL in the same file had the same problem: the server reads SPARSE_INDEX_INTERVAL (src/bin/server.rs:46).

Fix applied: docker-compose.yml now sets DATA_DIR=/data and SPARSE_INDEX_INTERVAL; the Dockerfile declares ENV DATA_DIR=/data and VOLUME ["/data"] so the image is durable without extra configuration.

C-04 — SSTable corruption detection and quarantine are wired to inverted signals

Status: filed as an issue.

Table::from_sstable_path (src/core/table.rs:89) handles a failed meta-block read as Err(_) => (Vec::new(), Vec::new(), None) (src/core/table.rs:113) and returns Ok. It returns Err only when the meta block was read and the bloom filter then failed to deserialise.

discover_sstables_from_disk (src/core/engine/mod.rs:2993) quarantines on Err — moving the file into sstables/quarantine/. The two are therefore inverted:

  • A genuinely unreadable SSTable (wrong key, truncated meta block, bit rot) returns Ok and is registered with an empty min/max key range and no bloom filter. Key pruning treats it as covering nothing, so its data becomes invisible. No warning, no quarantine, no metric.
  • A file whose meta block reads fine but whose bloom filter fails to deserialise returns Err and is moved out of the data directory on startup.

The same function also carries the comment "For now, we'll create an empty table - in production this would read the SSTable" (src/core/table.rs:94), and is called from five sites including the compaction and snapshot-restore paths.

High

H-01 — X-Forwarded-For is trusted unconditionally

Status: filed as an issue.

get_client_ip (src/api/rate_limiter.rs) returns the first address in X-Forwarded-For whenever the header parses, with no trusted-proxy allow-list and no way to disable the behaviour. Any client can therefore:

  • Bypass rate limiting entirely by varying the header per request; each forged value gets its own fresh budget.
  • Grow the tracking map without bound. shard.retain(...) only drops entries whose timestamp window has emptied, so one request per forged address keeps an entry alive for 60s. Millions of forged addresses are millions of live IpTrack values.
  • Forge audit-log attribution, since the audit middleware resolves the client the same way.

.expect("rate limiter shard lock poisoned") on the same path turns any panic under the lock into a process abort (see H-04).

H-02 — Per-endpoint rate-limit counters never decay

Status: filed as an issue.

IpTrack::prune (src/api/rate_limiter.rs) trims timestamps to the 60-second window but leaves endpoint_counts untouched; the comment says the counters are "pruned implicitly when the whole IpTrack is removed", which requires timestamps to become empty.

The middleware records a timestamp on every request, so any client sending at least one request per minute never empties the window, and endpoint_counts increases monotonically for the process lifetime. Once count >= limit, is_rate_limited returns true forever: a legitimate client that trips a per-endpoint limit once is locked out of that endpoint permanently. The window does not slide.

endpoint_counts is also keyed on the raw req.path(), so /keys/<random> generates an unbounded number of map entries per client.

H-03 — WAL recovery deduplication discards range tombstones

Status: filed as an issue.

deduplicate_records (src/storage/wal.rs:789) keys on (column_family, key) and keeps the last occurrence. LogRecord::range_tombstone(start, end) sets key = start (src/core/log_record.rs:95).

So a range tombstone and any point write to its start key collide. Replaying

delete_range(b"a", b"z")
put(b"a", v)

keeps only the put, dropping the tombstone — and with it the deletion of every key in b"b" ..= b"y". Deleted keys silently reappear after a restart.

The dedup pass was introduced for issue #191 (stale value after restart) before range deletes landed in #192; the two were never reconciled.

H-04 — panic = "abort" makes every catch_unwind recovery path dead in release

Status: filed as an issue.

Cargo.toml sets panic = "abort" under [profile.release]. catch_unwind cannot catch anything when panics abort, so in release builds:

  • The whole src/infra/panic_recovery.rs module is inert, including spawn_protected, the panic history, and the on_panic callbacks.
  • The compaction thread guard at src/core/engine/mod.rs:1876 does not protect anything: a panic during compaction takes down the server.
  • Every .expect(...) and slice index in a request path becomes a process kill.

This only manifests in release. Tests run under the dev profile with unwinding, so the suite exercises code that cannot behave that way in production. For a server that documents resilience features (circuit breaker, degradation manager, watchdog), panic = "abort" and panic_recovery are mutually exclusive; one has to go.

H-05 — Two live RustSec advisories; the CI audit job cannot run

Status: one fixed, one accepted with a recorded rationale; tooling fixed.

cargo audit with the version pinned by the toolchain (0.21.2) aborts before scanning:

error: error loading advisory database: parse error:
  .../libcrux-aesgcm/RUSTSEC-2026-0211.md: unsupported CVSS version: 4.0

Both CI audit steps therefore produce no signal, which is why the following went unnoticed. With cargo-audit 0.22.2:

IDCrateIssue
RUSTSEC-2026-0258h2 0.3.27unbounded empty DATA frames (DoS) — fixed in >= 0.4.16
RUSTSEC-2026-0222wasmtime 44.0.2stores mix up type indices between engines (3.8 low)

h2 0.3 sits directly under the HTTP server, so the DoS is reachable.

Thirteen warnings accompany them, including spin 0.9.8 yanked, and ring 0.16.20 / rustls-pemfile 1.0.4 unmaintained. Those two come from rustls = "0.20", and .cargo/audit.toml ignores their advisories with the justification "Cannot upgrade without upstream actix-web upgrading rustls". That is no longer true: actix-web 4.12 exposes a rustls-0_23 feature. Moving to it drops ring 0.16 from the tree and makes both ignores unnecessary.

The dependency graph also carries three simultaneous major versions of rand (0.7.3, 0.8.5, 0.9.2) across 573 crates.

Resolution. actix-web's rustls feature is an alias for rustls-0_20; switching to rustls-0_23 removed rustls 0.20, tokio-rustls 0.23, ring 0.16 and rustls-pemfile 1 from the tree, so both entries in .cargo/audit.toml are gone rather than re-justified. wasmtime moved from 44 to 47.0.4, outside the RUSTSEC-2026-0222 range. cargo update cleared the yanked spin 0.9.8 and the anyhow, event-listener and memmap2 advisories. Dependencies went from 573 to 555 and audit warnings from 13 to 6.

RUSTSEC-2026-0258 (h2) cannot be fixed by a version bump: h2 0.3 comes from actix-http, which every actix-web 4.x release depends on, and the advisory's fix is h2 ≥ 0.4.16. It is now the single entry in .cargo/audit.toml, with the dependency chain, the exposure, the existing mitigations and a review date recorded in place of the previous unexplained ignore list.

Bumping wasmtime raised the MSRV to 1.94 (the cranelift crates require it). The pinned toolchain moved to 1.98, the current stable — 1.92 was never a deliberate choice, only the floor wasmtime 44 imposed. The two numbers are now distinct and separately checked: rust-toolchain.toml pins the toolchain, rust-version in Cargo.toml declares the MSRV, and the CI MSRV job verifies the latter independently.

The TLS wiring moved to the rustls 0.23 API. That also fixed a latent bug: the old code called rustls_pemfile::pkcs8_private_keys only, so an RSA (PKCS#1) or EC (SEC1) key was rejected with "No private key found". rustls_pemfile::private_key accepts all three.

H-06 — ci.yml runs no tests, no clippy and no build on main

Status: filed as an issue.

.github/workflows/ci.yml triggers on push to main and runs three jobs: actionlint, audit (currently broken, see H-05), and benchmark. There is no cargo test, no cargo clippy, no cargo build.

pr-validation.yml does have those jobs, and also triggers on push to main, so the two workflows duplicate the audit job on every push. benchmarks.yml adds a third clippy + fmt run. Meanwhile:

  • Every workflow uses container: rust:latest and dtolnay/rust-toolchain@stable — redundant, and unpinned, so a new stable release can break CI with no repository change. cargo clippy --all-features currently emits a warning on Rust 1.92, and CI runs with -D warnings.
  • No --locked anywhere, so Cargo.lock is not enforced.
  • No MSRV job, so the README's claim of Rust 1.70 was never tested (the real floor is 1.92).
  • latency_bench and write_amplification are declared in Cargo.toml but absent from the benchmarks.yml matrix, so they never run.
  • benchmarks.yml triggers on a develop branch that does not exist.
  • No coverage job, and no cargo fuzz job despite fuzz/ being present.

Medium

M-01 — Container health checks probe a route that does not exist

Status: fixed in this pass.

The registered routes are /health/liveness, /health/readiness, /health/startup and /health/check (src/api/mod.rs:1582-1585). There is no GET /health.

Both the Dockerfile HEALTHCHECK and the docker-compose.yml healthcheck probed http://localhost:8080/health, so both returned 404. Independently, the Dockerfile health check invoked curl, which the runtime image never installed — and used exec form (CMD ["curl", …, "||", "exit", "1"]), where || is passed as a literal argument rather than interpreted. Three separate reasons for the same probe to never succeed.

QUICKSTART.md:71 and docs/AUTHENTICATION.md:129 documented the same missing route.

Fix applied: curl added to the runtime image; both probes point at /health/liveness in shell form; both documents corrected.

M-02 — Documented environment variables did not match the code

Status: fixed in this pass, with a regression guard.

Diffing env::var(...) call sites in src/ against assignments in .env.example:

Read by the code, absent from .env.example (15): ACCESS_CONTROL_ENABLED, CORS_ENABLED, CORS_ORIGINS, DATA_DIR, ENVIRONMENT, MAX_CONNECTIONS_PER_IP, OTEL_EXPORTER_OTLP_ENDPOINT, REPLICATION_ROLE, REPLICATION_SYNC_INTERVAL_MS, REPLICA_ENDPOINTS, SPARSE_INDEX_INTERVAL, TLS_CERT_PATH, TLS_ENABLED, TLS_KEY_PATH, TLS_PORT.

Every TLS, CORS and access-control setting was undiscoverable — the security-relevant half of the configuration surface.

Documented, read nowhere (5): DIR_PATH, INDEX_INTERVAL, WAL_MAX_SIZE, WAL_ARCHIVE_ENABLED, WAL_CHECK_INTERVAL_SECS. Operators setting these got silence — which is how C-03 stayed hidden.

The README additionally advertised WAL_SYNC_MODE=async as giving "16x throughput". That variable appears nowhere in the codebase; the knob is the compile-time constant WAL_SYNC_INTERVAL (src/storage/wal.rs:139), with no environment binding at all.

Fix applied: .env.example rewritten to cover all 34 variables the code reads, with a commented block naming the ones that exist only as LsmConfig fields. scripts/check-env-example.sh (wired to make env-check) fails the build on future drift in either direction.

M-03 — README and QUICKSTART commands fail as written

Status: fixed in this pass.

  • README Quick Start said cargo run --release. With four binaries and no default-run, cargo refuses: "could not determine which binary to run".
  • README's TLS example used --bin server; QUICKSTART used --bin cli six times. Neither name exists — the binaries are apexstore-server, apexstore-cli, apexstore-tui. Every runnable command in QUICKSTART.md failed.
  • The Rust badge claimed 1.70+; --all-features needs 1.92.

Fix applied: binary names corrected throughout, default-run = "apexstore-server" and rust-version = "1.92" added to Cargo.toml, URLs and the badge updated.

src/main.rs remains a 13-line stub that builds an engine at a hardcoded /var/lib/apexstore/data and exits, producing the fourth binary apex-store-rs; removing it is filed separately.

M-04 — Benchmark automation commits an empty result on every run

Status: filed as an issue.

git log shows 20+ consecutive identical commits, docs: update benchmark results [skip ci]. The README block they write currently reads "No results parsed — check the run artifacts."

scripts/format_bench.py succeeds but yields an empty table, so benchmarks.yml takes the "no results parsed" branch, rewrites the same placeholder, and commits. The benchmark step itself is continue-on-error: true, so a failing benchmark still reaches the README rewrite. The result is history pollution plus a performance section that has not reflected reality since v2.1.39.

M-05 — CI pipes an unpinned remote installer into bash

Status: filed as an issue.

.github/workflows/benchmarks.yml runs:

curl -fsSL https://raw.githubusercontent.com/opencode-ai/opencode/main/install.sh | bash

Unpinned code from a third-party main branch, executed in a job that holds GITHUB_TOKEN and pushes commits to main. Whoever controls that branch controls this repository's CI.

M-06 — No test covers authentication, rate limiting or engine-level encryption

Status: filed as an issue.

Across the twelve files in tests/, grep finds no reference to auth, Bearer, token, rate_limit, or RateLimit. Only proptest_sstable.rs mentions encryption, at the block level.

That is precisely why C-01 was reintroduced without any test turning red, and why the suite runs entirely on zero-key encryption without noticing: restart.rs uses the default config, so it writes and reads with the same all-zero key and passes.

Also worth noting: examples/ contains a single file for a crate advertising 40+ features.

M-07 — The frontend has never compiled, and nothing noticed

Status: build errors fixed in this pass; the framework upgrade is filed as an issue.

No workflow referenced frontend, npm or node, so the 30-plus pages under frontend/src/app/pages/ were never built, linted, tested or dependency-scanned. Adding a Frontend job to CI turned it red immediately: npm run build fails on main. The dashboard has never produced a bundle.

Nine errors across seven files, all of the same family — standalone components must list every directive and pipe their template uses, and these do not:

FileErrorCause
vector-search.component.tsNG8002 ngClass, NG8004 pipe numbermissing NgClass, DecimalPipe
wasm-plugins.component.tsNG8002 ngClass ×2missing NgClass
tags.component.ts"not statically analyzable", NG8004 pipe sliceFormsModule imported from @angular/common, which does not export it, so it resolved to undefined; missing SlicePipe

The last one is not just a type error. SyncService.lastSyncTimestamp is a signal<number | null>, and the component did:

this.sync.lastSyncTimestamp.subscribe(ts => { ... });

Signals have no subscribe, so the callback never ran and the "last synced" label was permanently stuck on Never. The same component's auto-refresh timer called lastSyncedLabel.update(l => l) every five seconds, which writes the same value back — and signals compare for equality before propagating, so it notified nothing. Both are now replaced by a computed signal.

Two more surfaced once those were cleared, and both are cascades rather than counts:

  • server-config.component.html filtered inline with filtered().filter(c => c.group === group). Angular's template parser reads => as an assignment and rejects the binding (NG5002), so the filter had to move into the component.
  • graph.component.html used @else if (fetched() && graphData(); as data). as is only valid on a primary @if, so the binding never existed and all 33 references to data in that branch failed. The trailing @else if (fetched() && !graphData()) was also unreachable, since the branch before it already consumed every fetched() case.

And three that are logic bugs, not import hygiene:

  • pubsub.component.ts declared both a field publishMessage = '' and a method publishMessage(). The method's own body called this.publishMessage.trim(), which resolved to the method.
  • health.component.ts declared signal<'healthy' | 'degraded' | 'unhealthy'>('unknown') — an initial value outside its own union. resilience.component.ts did the same through its HealthSummary interface.
  • sync-status.component.ts imported Time05Icon and DataIcon, neither of which @hugeicons/core-free-icons exports, and its template used <app-hugeicons-icon> where the component's selector is hugeicons-icon.

After the fixes npm run build exits 0 with one warning: one component stylesheet is 157 bytes over Angular's default 2 kB budget.

npm audit on the installed tree reports 67 vulnerabilities (3 critical, 39 high).

frontend/package.json pins @angular/* ^17.3.0. Angular 17 left long-term support in 2025, so none of those get patched. karma is also deprecated in favour of the Angular CLI's own runner, and there are two spec files for thirty-plus components. frontend/Dockerfile exists but is absent from docker-compose.yml. The upgrade is tracked separately.

Low

L-01 — MemTable uses DashMap but exposes &mut self

src/core/memtable.rs stores data: DashMap<Vec<u8>, LogRecord>, but put, insert and friends take &mut self, and size_bytes is a plain usize field. Callers must hold an exclusive borrow, so the engine serialises access behind its own lock and DashMap's per-shard concurrency is never reached — the sharding overhead is paid without the benefit. Either move size_bytes to an atomic and take &self, or use a BTreeMap and drop the dependency. The README claim of "lock-free reads and writes to different keys" has been corrected in the meantime.

L-02 — Engine is a single 2300-line impl block

src/core/engine/mod.rs is 4935 lines, of which one impl<C: Cache> Engine<C> spans lines 855-3148. src/api/mod.rs is 1964 lines with all route handlers, middleware wiring and the transaction manager. Splitting along existing seams (reads, writes, snapshots, column families) would make the encryption and quarantine paths above far easier to reason about.

L-03 — Version number disagrees across three files

Cargo.toml says 2.2.7; ROADMAP.md says "Current Version: v2.3.0"; the Dockerfile label said 1.4.0; CHANGELOG.md has everything under [Unreleased] — v2.2 -> v2.3. The Dockerfile label is fixed; the rest needs a release-process decision.

L-04 — .gitignore contained *.sh

Status: fixed in this pass.

.gitignore ignored *.sh wholesale with a single !scripts/format-benchmarks.sh exception, so any new shell script a contributor wrote was invisible to git status. The pattern is now !scripts/*.sh, and *.pem / *.key were added so TLS material cannot be committed by accident. The ignore list also only covered .lsm_data, while CoreConfig::default() uses ./.lsmdata — both spellings are now listed.

.task-state.json and .apexstore/state.json are committed agent scratch state, duplicating each other and referencing issues closed months ago. They are now in .gitignore, but untracking them is filed separately since it changes repository contents.

  • H-05 "Rate Limiter Usa Mutex Simples (Gargalo)" — the limiter is now sharded 16 ways (NUM_SHARDS, src/api/rate_limiter.rs). The real defect is H-02 above.

They are also the only Portuguese documents in an otherwise English repository, which makes them invisible to most readers and to the published documentation site. docs/SUMMARY.md listed just four of the nine files under docs/, so AUTHENTICATION.md, CLI_GUIDE.md, PERFORMANCE.md, WORKFLOWS.md and both audits were never published to GitHub Pages at all; that is fixed in this pass.
